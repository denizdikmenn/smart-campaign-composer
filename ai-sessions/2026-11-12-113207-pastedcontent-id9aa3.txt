  ## 1. Architecture

  Implement delivery as a **separate Go worker executable**, within the
  existing backend and Go module.

  Use this structure as a starting point:

  ```text
  backend/
    cmd/
      api/
        main.go
      worker/
        main.go

    internal/
      delivery/
        queue.go
        worker.go
        provider.go
        retry.go
  ```

  Adapt to the existing code where appropriate. Avoid unnecessary files,
  packages, and abstractions.

  The API and worker are separate processes/containers sharing the existing
  PostgreSQL database.

  - **API:** Campaign approval, dispatch initiation, recipient resolution, job
  creation, monitoring endpoints.
  - **Worker:** Claim queued jobs, enforce rate limits, call mock providers,
  handle retries, persist delivery results.
  - **PostgreSQL:** Durable delivery queue and source of truth for delivery
  state.
  - **Vue:** Campaign send action and live monitoring interface.

  Do not introduce Redis, RabbitMQ, Kafka, an external queue, a second Go
  module, or an HTTP communication layer between the API and worker.

  The worker does not need a public HTTP port.

  Add the worker to the existing Docker Compose development and production
  configurations. Preserve current `make dev`, `make up`, and `make test`
  behavior.

     Context

     Everything up to approval already works: segmentation, drafts, A/B,
     localization, groups, individual personalization, the recipient plan, and
     approval with a frozen approved_snapshot. The remaining steps from
     REQUIREMENTS.md are 5 (async delivery through mock SMS/email providers) and
     6 (live monitoring). The deliveries table and delivery.Breakdown were
     already added for this but nothing writes to them yet. Plan: add a separate
     Go worker that uses PostgreSQL as the queue, an explicit Send action, and
     a monitoring view that polls once a second. All four strategies go through
     the same pipeline.

     Key findings that shape the design

     - content/resolve.go: resolver.resolve(member) is pure and already checks
       per-channel consent. It covers variant hashing (variantFor), language
       fallback, group and individual content, and Render. buildResolver reads
       from the current View, not the snapshot.
     - After approval the campaign is immutable: mutate() rejects approved
       campaigns. Snapshot (review.go) holds Draft, Variants[].Draft, Groups
       (with content) and Audience. Individual messages live only in
       personalized_messages, which is frozen after approval because Approve
       blocks while generation runs.
     - deliveries already has UNIQUE (campaign_id, customer_id, channel) and
       columns for variant, group, language and source. The status CHECK has
       delivered, which we will not fabricate. It has no skipped or retrying.
     - ReviewPanel skips loading /review once the campaign is approved. The
       router is a static hash router, and there is no campaign list endpoint.

     Backend

     Schema (backend/internal/db/schema.sql, idempotent appends)

     - campaigns.dispatched_at timestamptz: set once, inside the dispatch
       transaction.
     - deliveries: replace the status check (DROP CONSTRAINT IF EXISTS
       deliveries_status_check + ADD) with queued | sending | retrying | sent |
       failed | skipped. Add next_attempt_at timestamptz NOT NULL DEFAULT now(),
       locked_until timestamptz, sent_at timestamptz, provider_message_id text,

     Content: snapshot-based resolution (internal/content/resolve.go)

     - snapshotResolver(ctx, id) (View, *resolver, error): parse
       approved_snapshot and build the resolver from snap.Draft, snap.Variants,

     internal/delivery/

     - queue.go
       - Dispatch(ctx, pool, id, src MessageSource) (Report, error): in one
         transaction, SELECT status, dispatched_at FROM campaigns … FOR UPDATE.
         Not approved returns ErrNotApproved (409). If dispatched_at is already
         set, return the current report without creating anything, which makes
         the call idempotent. Otherwise collect messages via src (API passes
         content.Service.ApprovedMessages). Zero messages returns
         ErrNoRecipients. Then a chunked INSERT … SELECT FROM unnest(...) ON
         CONFLICT DO NOTHING (body and subject copied in, so later draft edits
         can't matter), then UPDATE campaigns SET dispatched_at = now(), then
         commit.
       - Claim(ctx, pool, channel, n, lease): a single autocommit UPDATE … WHERE
         id IN (SELECT … WHERE channel=$1 AND ((status IN ('queued','retrying')
         AND next_attempt_at<=now()) OR (status='sending' AND
         locked_until<now())) ORDER BY next_attempt_at, id LIMIT $2 FOR UPDATE
         SKIP LOCKED) RETURNING …. It sets status='sending' and locked_until,
         and sets attempts = attempts + CASE WHEN status='sending' THEN 0 ELSE 1
         END. A crashed attempt is resumed under the same key rather than
         counted again. No transaction stays open during provider calls.
       - Report(ctx, pool, id) reuses Breakdown rows folded in Go into totals,
         per-channel, per-variant and per-group counts (total, queued, sending,
         retrying, sent, failed, skipped, retries). It adds the top error
         reasons (last_error for failed and retrying), the next retry time,
         dispatched_at, and the worker heartbeat. Status: not_sent | queued |
         sending | completed | completed_with_failures.
       - Metrics(ctx, pool): global queue depth (due, scheduled retries, in
         flight, oldest due age), status×channel counts, sent in the last 60s
         per channel, total attempts, and worker heartbeat age.
     - provider.go
       - Provider interface Send(ctx, Request{Key, Channel, To, Subject, Body})
         (Response{Status, RetryAfter, MessageID}, error).
       - Mock{Channel, pool, Latency, Faults func(req, call int) Fault}. A fault
         can be 429 with Retry-After, 5xx, 4xx, or "lost response" (accepted,
         then a timeout error, the ambiguous case). Acceptance means INSERT INTO
         mock_provider_messages ON CONFLICT DO NOTHING and returning the
         existing message ID on replay.
       - RandomFaults(rates, seed) is the default for the running worker. Tests
         use scripted faults, so nothing depends on randomness.
     - retry.go
       - MaxAttempts = 4. Decide(resp, err, attempts, rnd) Outcome{Status,
         NextAt, Error}: 2xx means sent. 429 uses Retry-After (capped at 60s),
         falling back to backoff. 5xx and network/timeout errors use backoff of
         2s·2^(n-1), ±20% jitter, capped at 30s. Other 4xx fail immediately.
         Exhausted attempts fail with "gave up after 4 attempts: …".
       - The key is always delivery-{id} and never regenerated.
       - Backoff base is a field, so tests can use milliseconds.
     - worker.go
       - Worker{pool, providers map[channel]Provider, rate, concurrency, lease,
         backoff}. Run(ctx) starts one loop per channel. Each loop claims up to
         concurrency jobs and feeds a fixed pool of concurrency goroutines. When
         nothing is due it sleeps for a poll interval (~250ms). A heartbeat
         upserts every 5s.
       - process(job):
         i. Re-read the customer's consent and address. Revoked, missing, or
            deleted means skipped ("consent withdrawn before send"), with no
            retry.
         ii. limiter.Wait.
         iii. Call the provider with its own timeout, detached from shutdown so
              in-flight sends finish.
         iv. Decide.
         v. UPDATE … WHERE id=$1 AND status='sending' (status, next_attempt_at,
            last_error, sent_at, provider_message_id, locked_until=NULL).
       - Rate limiter (in worker.go, ~15 lines): a mutex-guarded "next slot"
         reservation spaced 1s/rate apart per channel, so attempt starts never
         exceed 100/s for each channel independently, including retries. A
         single worker replica is documented as the deployment assumption.
     - cmd/worker/main.go: reads env (DATABASE_URL,
       DELIVERY_RATE_PER_SECOND=100, DELIVERY_CONCURRENCY=10,
       MOCK_PROVIDER_FAULTS=on/off, MOCK_FAULT_SEED), migrates, and runs until
       SIGTERM. A -healthcheck flag exits 0 if the heartbeat is under 30s old
       (used by Docker).

  How it works:
  - Send. One transaction locks the campaign row and checks it's approved and
    not yet sent. It then works out each recipient's message from the approval
    snapshot, re-reading the audience and consent at send time, and stores one
    job per recipient and channel with the final text. Variant, group, language
    and content source are fixed on the job when it's created. The API returns
    202 right away. Repeated or concurrent Sends create nothing new, and the
    existing unique constraint is a backstop.
  - Worker. It claims jobs with FOR UPDATE SKIP LOCKED and a 30-second lease,
    and no transaction stays open during provider calls. If a worker crashes,
    the job is picked up again under the same idempotency key without counting
    an extra attempt. Consent is checked again right before each send; withdrawn
    consent marks the job skipped.

    retries included. This holds for a single worker replica, which is what
    Compose runs.
  - Retries. Up to 4 attempts. A 429 waits for Retry-After; 5xx errors and
    timeouts back off exponentially with jitter; other 4xx errors fail at once.
  - Idempotency. The mock provider records accepted keys in a table, so a retry
    after a lost response is accepted only once, even across restarts.
    DECISIONS.md states that this is exactly-once only with a provider that
    honours keys; otherwise there's a small at-least-once window.
