     Plan: minimal persistent tracing for the segmentation pipeline

     Context

     POST /api/segmentation/suggest (brief → Claude → validate → compile →
     count) leaves no record: when Haiku misuses a field or a count looks off we
     only have a transient log line, and there is nothing to build an eval set
     from. Goal: persist one row per suggest request with enough to debug and
     later replay/score, and nothing more (no spans, no tracing library, no UI,
     no extra endpoints).

     Design: one table, one insert per request

     Add to backend/internal/db/schema.sql (idempotent, runs on startup via
     db.Migrate):

     CREATE TABLE IF NOT EXISTS segmentation_runs (
         id              bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
         created_at      timestamptz NOT NULL DEFAULT now(),
         brief           text        NOT NULL,
         source          text        NOT NULL,            -- 'claude' | 'mock'
         model           text,
         status          text        NOT NULL,            -- ok | no_valid |
     refusal | auth_error | unavailable | bad_reply | error
         error           text,
         llm_ms          integer,                         -- Claude call only
         total_ms        integer     NOT NULL,            -- whole request
         input_tokens    integer,
         output_tokens   integer,
         raw_output      text,                            -- Claude's raw JSON,
     capped at 32 KB (untrusted)
         alternatives    jsonb       NOT NULL DEFAULT '[]', -- final validated
     results incl. counts
         warnings        jsonb       NOT NULL DEFAULT '[]'  -- dropped
     alternatives + why
     );
     CREATE INDEX IF NOT EXISTS segmentation_runs_created_idx ON
     segmentation_runs (created_at DESC);
     Why these columns: brief + raw_output + alternatives + warnings give input
     → raw LLM output → validated result, which is exactly what an eval needs
     (replay the brief, compare conditions/counts); status/error/timings/tokens
     cover debugging and cost. Prompt text is not stored (it is reproducible
     from code + catalog); store nothing secret (API key never touches this
     path).

     Code changes (all small)

     1. internal/segmentation/generator.go: change Generator.Generate to return
        a small GenResult{Alternatives []Alternative; Raw string; InputTokens,
        OutputTokens int} (+ error). Claude fills Raw from the text blocks and
        tokens from resp.Usage, and returns Raw even when parsing/validation of
        the reply fails. Mock returns the alternatives only (Raw empty).
     2. internal/segmentation/trace.go (new, ~50 lines): type run struct{...},
        statusOf(err) string (maps
        ErrNoValidAlternatives/ErrRefusal/ErrAuth/ErrRetry/ErrBadReply/other →
        status strings), and (*Service).record(run) doing one INSERT.
        - Uses context.WithoutCancel + 3s timeout so a client abort still
          records the run.
        - A failed insert only slog.Warns; tracing never fails or slows the user
          request meaningfully (inserted before returning, single row).
     3. internal/segmentation/service.go: in Suggest, start := time.Now(), time
        the gen.Generate call, and defer the record so every exit path (success,
        no-valid, refusal, auth, DB error) is captured. Add run_id to Response
        (set after insert, omitted if insert failed) so a UI/bug report can
        reference a run. Service needs a *slog.Logger (pass through NewService;
        one call site in cmd/api/main.go).
     4. Not traced: /preview (cheap, no LLM), and no changes to the frontend.

     Reading traces (no new endpoint)

     Documented one-liners via psql, e.g. recent failures:

❯ # Improve Segmentation Reliability, Evaluation & UX

  Read `docs/REQUIREMENTS.md`, `CLAUDE.md`, and inspect the existing
  segmentation pipeline, validation logic, execution traces, and Vue interface
  before making changes.

  The current implementation works for straightforward campaign briefs, but we
  need to make it more reliable when users provide ambiguous, unsupported,
  contradictory, or unexpected requests.

  The goal is not to build a sophisticated AI safety system. We want a simple,
  trustworthy marketing tool that knows when it can fulfill a request, when it
  needs clarification, and when it cannot accurately generate an audience.

  ## 1. Improve Validation and Reliability

  Our current backend validation mainly checks whether individual conditions
  contain supported fields, operators, and values. This is useful, but it does
  not guarantee that the generated audience makes sense or represents the
  original brief.

  Improve the pipeline across four responsibilities.

  ### Structural Validation

  Keep the existing schema and field/operator allowlist approach, but close
  obvious gaps.

  - Reject malformed, incomplete, or incompatible condition values.
  - Reject unexpected values in fields that should not contain them.
  - Enforce integer values for counts and day-based conditions where
  appropriate.
  - Require meaningful alternative names and explanations.
  - Keep existing limits on numbers, lists, and conditions.
  - Return understandable validation errors.

  Do not replace the existing implementation with a generic validation
  framework.

  ### Logical Validation

  Detect obvious contradictions, redundant conditions, and impossible
  combinations.

  Examples:
  - `order_count = 0` AND `order_count >= 5`
  - `total_spent >= 10000` AND `total_spent <= 1000`
  - Conflicting city inclusion/exclusion rules
  - Redundant conditions that do not affect targeting

  Keep this practical. We do not need a generic constraint solver or exhaustive
  logical reasoning engine.

  Distinguish between an invalid segment and a valid segment that happens to
  match zero customers.

  ### Intent and Capability Verification

  The system must recognize when a user's request cannot be represented
  accurately with the available customer data and supported segmentation
  capabilities.

  Examples:
  - Subscription cancellation cannot be inferred from inactivity.
  - Country targeting cannot be inferred from city or language.
  - Spending during the last 30 days is not equivalent to lifetime spending.
