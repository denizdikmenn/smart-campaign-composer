❯ # Evaluation Strategy — Real-World Hardening, Not Happy-Path Verification

  We already have segmentation evaluations in place. Extend the existing
  evaluation approach to campaign generation/regeneration, localization,
  behavioral grouping, individual personalization, and critical end-to-end
  workflows.

  **The primary objective is to discover weaknesses in the system, not to
  demonstrate that the current implementation works.**

  ## 1. Design Tests Independently of the Implementation

  Inspect the existing system to understand its behavior, interfaces, and
  limitations, but do not use its current prompt, supported examples,
  validation rules, or implementation details as the basis for choosing
  evaluation scenarios.

  Start from realistic marketer intentions, customer situations, and business
  requirements.

  Think about how actual users would interact with a marketing platform,
  including imperfect instructions, ambiguous feedback, changing decisions,
  incomplete information, and unexpected combinations of requirements.

  Do not restrict scenarios to what the current implementation can already
  handle.

  A test exposing an unsupported capability is valuable. Do not rewrite it into
  a supported example simply to make it pass.

  **Define expected behavior before executing the test. Never adjust
  expectations afterward to match the system's output.**

  ## 2. Prioritize Scenario-Based Hardening

  Avoid simple preset-style tests such as:

  - Generate a friendly SMS.
  - Translate a message into Turkish.
  - Create three customer groups.
  - Personalize a message using the first name.

  These are useful smoke tests but provide little confidence in real-world
  reliability.

  Instead, evaluate realistic workflows where several requirements interact.

  ### Generation & Regeneration — 10–15 scenarios

  Focus on multi-turn marketer interactions:

  - Campaign requirements changing across regenerations
  - New promotions being introduced, modified, or withdrawn
  - Contradictory or ambiguous feedback
  - Preserving manual edits and unrelated content
  - Channel-specific instructions
  - Incorrect assumptions about offers, dates, or eligibility
  - Previous instructions accidentally leaking into newer drafts
  - Interrupted generation and draft recovery

  Evaluate complete interaction sequences, not just isolated prompts.

  ### Localization — 3–4 scenarios

  Use realistic multilingual communication challenges:

  - Mixed-language briefs and feedback
  - Brand names, coupon codes, currencies, and product terminology that must

  ### Results and Reporting

  Save results as ordinary files in the repository, for example:

  ```text
  evals/
    hardening/
      scenarios.json
      run.go (or reuse existing runner)
      reports/
        latest.md
        latest.json
  ```

  Adapt this layout to the existing repository. Do not create parallel tooling
  when an existing runner can be reused.

  **No database persistence is needed.**

  The Markdown report should be immediately understandable without opening raw
  logs or JSON files.

  Include:

  1. **Overview:** Number of scenarios run, passed, failed, needing review, and
  not run.
  2. **Results table:** Scenario name, expected behavior, actual behavior,
  status, and short explanation.
  3. **Key failures:** The most important issues, with brief examples of the
  model's actual output.
  4. **Recommendations:** A few prioritized, actionable improvements.
  5. **Execution summary:** Model, approximate token usage/cost, and execution
  duration when available.

  Use simple statuses: `PASS`, `FAIL`, `REVIEW`, `NOT RUN`.

  Keep detailed outputs in JSON for debugging, but make the Markdown report the
  primary review artifact.

  Do not dump enormous prompts or full API traces into the Markdown report.

  ### Working Approach

  1. Inspect existing eval tooling and reuse what is useful.
  2. Design realistic hardening scenarios independently of the current happy
  paths.
  3. Define expected behavior before execution.
  4. Run the applicable scenarios with minimal API calls.
  5. Save a concise Markdown report and machine-readable JSON results.
  6. Report the main findings in the final response.

  **Do not automatically start a large hardening/refactoring cycle.** This task
  is about building and running the evaluation suite and reporting what it
  reveals. Fixes can be handled separately after reviewing the results.

  Avoid repeated retries, unnecessary infrastructure work, and exhaustive
  attempts to make every scenario pass.

  If something is blocked, record it as `NOT RUN`, explain why, and continue
  with the remaining scenarios.

  ### Final Response

  Keep the final response short:

  - Scenarios executed and pass/fail/review counts
  - 3–5 most meaningful findings
  - Recommended fixes, prioritized
  - Location of the saved Markdown report

  The goal is a **small, independent, realistically challenging eval suite with
  easily reviewable results**, not another testing project.

  A few genuine failures with clear explanations are more valuable than 100%
  passing tests tailored to the current implementation.

     Context

     Segmentation already has an opt-in real-Claude eval (eval_test.go
     (backend/internal/segmentation/eval_test.go): case table, env gate,
     PASS/FAIL logs). Content generation, localization, grouping and
     personalization have none. The goal is a small, separate suite of
     realistic, adversarial scenarios. Expected behavior is fixed before any
     run. The suite runs once to get a baseline and writes a readable report. It
     does not fix anything.

     Approach: copy the segmentation eval pattern into internal/content

     One new file, backend/internal/content/hardening_eval_test.go, using the
     same package so it can call the real *Claude methods directly:
     - Generate(ctx, Request{Brief, Audience, Base, Feedback, Language, Intent},
       onDelta). For multi-turn runs, each turn's Reply becomes the next turn's
       Base, and manual edits are applied to Base between turns.
     - Translate(TranslateRequest), ProposeGroups(GroupsRequest),
       Personalize(PersonalizeRequest) from calls.go
       (backend/internal/content/calls.go).
     - Every output goes through the deterministic Validate(content, brief,
       maxNameLen) from validate.go (backend/internal/content/validate.go). The
       report records whether the backend accepted it, so a "backend accepted
       invalid output" failure can be told apart from "the model got it wrong".
     - Grouping profiles are built by describeProfile([]segmentation.Member,
       now) (groups.go:317 (backend/internal/content/groups.go#L317)) from
       hand-built members, so no DB is needed. Proposed groups then go through
       the existing group validation/compile path. Deterministic assignment,
       non-overlap and coverage need Postgres. If DATABASE_URL is set, they run
       through sizeGroups/reachableMembers. If not, they are recorded as NOT
       RUN.
     - Gate: HARDEN_EVAL=1 + ANTHROPIC_API_KEY. HARDEN_EVAL_ONLY=G03,L01 filters
       scenarios. Normal go test skips the suite.

     Each scenario struct holds: id, area, intent, expected (written prose shown
     in the report), turns, plus deterministic checks: mustContain /
     mustNotContain (codes, amounts, dates, brand names, case-insensitive per
     field), validateMustBlock, wantOutcome for groups (groups/not_meaningful),
     and review bool for judgements that need a person. Status values: PASS /
     FAIL / REVIEW (deterministic checks pass but a rubric item needs a human) /
     NOT RUN (feature missing or infra unavailable). A failure also records a
     category (model misunderstood, omitted/invented, unsupported not
     recognized, validation accepted invalid output, …).

     Output: the test writes evals/hardening/reports/latest.json (full outputs,
     raw model text, token counts) and latest.md with these sections: overview
     counts, results table, key failures with short excerpts, recommendations (I
     write these by hand after the run), and execution summary (model, tokens,
     cost at list price, duration). The scenarios and expectations stay in Go
     next to the checks. No separate scenarios.json, so there is no second
     source of truth.

  REVIEW, 2 NOT RUN. That run cost about 85k tokens (≈ $0.02) and took 2.3

  The two NOT RUN cases are interrupted-generation recovery and group-assignment
  determinism. Both need Postgres or the streaming layer, and the existing
  tests already cover them.

  The suite ran three times. The first full run showed every proposed group as
  invalid. That was a bug in my test code, not the app: it skipped a validation
  step that production runs. I fixed it and re-ran the groups, then re-ran
  everything once so the report comes from a single run. No expectations were
  changed.

  My own checker also produced a false failure on B03: a word list meant to
  catch purchase claims matched "Recent cart shoppers". After reading the output
  I judged B03 acceptable. The report notes this alongside the automatic
  status.

  Main findings:
  1. Wrong offer for the audience (G08, most serious): a "100 TL off your first
     order" welcome code went to customers with 4+ orders. It passed in one run
     and failed in the other. In neither run did the system point out the
     conflict to the marketer.
  2. Ignored feedback goes unreported (G07, G12): the model quietly dropped an
     impossible instruction ("the sale ended yesterday") and requests for an
     image and countdown timer. The output is safe, but the marketer is never
     told their request wasn't applied.
  3. Warnings on legitimate offers (G03, G13): the backend compares facts only
     against the original brief. A code or amount the marketer adds in feedback
     (WINTER25, 750 TL) gets flagged every time as "make sure it is a real
     offer".
  4. Too-small audiences get split (B02): 22 customers were divided into 3
     groups of about 5–8. The current minimum before grouping is allowed is 20
     customers.
  5. What held up: offers changed or withdrawn, manual edits, channel-only
     instructions, old campaign wording leaking into new drafts, internal notes
     left in an edit, brand names and codes in translation, and personalization
     without invented personal details all passed.

  Recommended fixes, in priority order:
  1. Detect brief-vs-audience eligibility conflicts in application code (e.g.
     "first order" with an audience of past buyers) and show them as a warning.
  2. Add an optional notes field to the regeneration reply so the model can tell
     the marketer when it didn't apply something.
  3. Count marketer feedback as a valid source of facts in the validation step.
  4. Raise the grouping minimum based on group count, or tell the model the
     smallest acceptable group size.
  5. Low priority: stop the model adding opt-out lines like "Reply STOP to opt
     out" that the brief didn't ask for.

⏺ I fixed all four main findings in application code. On a full re-run of the
  same 25 scenarios, the result went from 14 PASS / 3 FAIL / 8 REVIEW to 16 PASS
  / 0 FAIL / 9 REVIEW; 2 scenarios still need the DB and weren't run. Go tests,

  type-check pass. Each fix has a regression test in hardening_fixes_test.go
  (backend/internal/content/hardening_fixes_test.go).

  Finding: G08 "first order" offer sent to repeat buyers
  Fix: New blocking eligibility_mismatch check (validate.go
    (backend/internal/content/validate.go)). It fires when the copy, in any
    language, mentions a first order or new customer and every audience rule
    requires a past order. It appears in the editor next to the channel issues
    and blocks approval.
  Result: PASS. The model also dropped the offer and explained why.

  Fix: Optional notes field in the generation reply, shown through the existing

  Finding: G03/G13 codes and amounts the marketer added in feedback flagged as

  - Empty replies: at first, about 3 in 40 first drafts came back with every

  - JSON leaking into the SMS: once, the model put JSON syntax (','notes':)
    inside the SMS text. A new guard in all three reply parsers rejects these.
    The marketer gets Retry and the previous draft is kept.

  - Eval code changes: I updated the eval to match the new production behaviour
