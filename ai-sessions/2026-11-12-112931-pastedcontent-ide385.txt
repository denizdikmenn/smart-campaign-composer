⏺ The schema and a deterministic 5,000-customer seed are in place and checked
  against a running PostgreSQL 18. The new tests pass, and make test passes with
  the existing API tests and the frontend type-check.

  Schema decisions

  The schema is in backend/internal/db/schema.sql. It has three tables:

  - customers: email_consent and sms_consent are separate booleans, NOT NULL,
    defaulting to false, so consent is opt-in and each channel is independent.
    - CHECK (NOT sms_consent OR phone IS NOT NULL) means a customer can't be
      SMS-consented without a number.
    - Emails are unique and must be lowercase. Phones are optional, unique, and
      in E.164 format.
  - orders: each row is one purchase, with a category, an amount (numeric(10,2),
    must be above 0), and a timestamp.
  - cart_additions: these are kept apart from orders. That is what lets a rule
    say "added to cart in the last 30 days, no purchase since".
  - Indexes: city, (customer_id, time) on orders and cart additions, and
    added_at.
  - No stored aggregates: things like total spend are computed by queries, so
    they can't drift out of date.
  - Foreign keys: these cascade on delete.

  How the seed works

  - The API applies the schema on every start. If customers is empty, it loads
    SEED_CUSTOMERS customers (default 5000, set in Compose; 0 disables).
  - The random seed is fixed, so the same count and "now" always give the same
    data. Timestamps are relative to the start day, so "last 30 days" segments
    stay populated.
  - Customer emails use only reserved example.* domains, so nothing can reach a
    real person. Phone numbers are random in Turkish mobile format and could
    coincide with real ones. The mock providers mean none are contacted.
  - I put migration and seeding in API startup instead of a separate seed
    service. It avoids another container and image, and it works with hot
    reload. The trade-off is that the API refuses to start if the database is
    unreachable, which was not true before.

  Verified

  - Tests: gofmt and go vet are clean.
    - Generator tests check determinism, uniqueness, valid timestamps, reserved
      email domains, and distribution bounds.
    - Database tests ran in a throwaway schema on the real Postgres and were not
      skipped. They cover repeat migration, seeding, no re-seed, the identity
      sequence after the seed, and rejection of bad rows (SMS consent without a
      phone, uppercase email, malformed phone, an order for an unknown
      customer).
    - Both email-only and SMS-only customers are accepted.
  - Live stack: on a fresh volume, make up produced 5,000 customers, 21,477
    orders and 5,125 cart additions.
    - Consent: both channels 40.3%, email only 37.6%, SMS only 11.6%, neither
      10.6%. 298 customers have no phone, and none of them has SMS consent.
    - Cities: Istanbul 29.2%, Ankara 11.7%, Izmir 9.5%, then a tail.
    - Orders per customer: 786 have none, 1,782 have 1–2, 1,506 have 3–6, 690
      have 7–15, and 236 have 16 or more. Order totals run from 20 to about
      20,132, with a median of about 584.
    - Abandoned carts: 602 customers added to cart in the last 30 days with no
      later order. Of those, 169 are in Istanbul and 131 of the Istanbul ones
      consent to email, so the example campaign brief has a real audience.
  - Restart and rebuild: restarting the backend did not re-seed. The same data
    hash after a restart and after rebuilding from a fresh volume confirms the
    seed is deterministic.

  Caveats

  - No migration tool: the schema is a single idempotent file, so changing an
    existing table later would need a real migration step.
  - No consent history: consent is a plain boolean with no timestamp or audit
    trail.
  - Postgres after tests: make test now starts Postgres for the database tests
    and leaves it running.
  - Wiped data volume: I deleted the dev data volume while testing, so the first
    run reseeded.
  - README: I added a short Data section covering the seed and how to reseed.

  Schema

  customers gains two columns:
  - language: an ISO 639-1 code, default tr, for later message generation.
  - last_active_at: last visit, cart or purchase. I made it a column because
    visits aren't stored as events.

  orders, cart_additions and the existing columns are unchanged. schema.sql also
  adds both columns with ALTER ... ADD COLUMN IF NOT EXISTS, so a database
  created before this change can still run the schema (it gets default values,
  not the new seed data).

  Seed

  The generator now builds each customer from one of eight behavior types: VIP,
  loyal, recent buyer, lapsing, win-back, cart abandoner, new, and dormant.
  Order and cart histories follow from the type, and last_active_at is never
  before a customer's latest event. About a third of orders are preceded by a
  cart addition.

    customer. Consent and city filters combine with the audience.
  - GET /api/customers/summary: gains buyers, repeat buyers, 30-day active
    customers and average order value.

  An unknown segment, or category_buyers without a category, returns 400.

      40 +## Data and audiences                                          
      41 +                                                               
      42 +On startup the API applies `backend/internal/db/schema.sql` (id
         +empotent) and, if `customers` is empty, loads                  
      43 +`SEED_CUSTOMERS` (default 5000; `0` disables) customers with or
         +ders and cart events from `backend/internal/seed`.             
      44 +The seed is deterministic for a given count and day, and builds
         + histories from behavioural archetypes (VIPs, cart             
      45 +abandoners, lapsed buyers, new customers, ...) so they are cohe
         +rent. Emails use reserved `example.*` domains.                 
      46 +                                                               
      47 +Audiences are fixed server-side definitions in `backend/interna
         +l/customers/audience.go`, expressed as parameterized           
      48 +SQL. They can overlap, and email and SMS consent are counted se
         +parately:                                                      
      49 +                                                               
      50 +| Audience | Definition |                                      
      51 +|---|---|                                                      
      52 +| Abandoned carts | Added to cart in the last 30 days, no purch
         +ase since |                                                    
      53 +| Win-back | Bought before, last order over 90 days ago |      
      54 +| VIP | 4+ orders and 5,000+ TRY lifetime spend |              
      55 +| Category buyers | Bought the chosen category in the last 180 
         +days |                                                         
      56 +| New customers | Joined in the last 30 days, no purchase |    
      57 +| Inactive visitors | Never purchased, not active in the last 6
         +0 days |                                                       
      58 +                                                               
      59 +The seed only runs on an empty table. After changing the schema
         + or seed, reset the data:                                      
      60 +`make down && docker volume rm smart-campaign-composer_postgres
         +_data`.
